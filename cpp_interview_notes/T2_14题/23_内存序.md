# 23 内存序 acquire / release 大概干嘛

## 面试口述版

两个独立的问题：**原子性**（这个操作是不是一步完成）和**可见性/顺序**（别的核什么时候、按什么顺序看到它）。
atomic 默认的 `seq_cst`（顺序一致）把全程序所有 seq_cst 操作排成一条全序，最直观也最慢。
`memory_order_release`（写端）+ `memory_order_acquire`（读端）组成**同步对**：
release 写把"它之前的所有读写"对 acquire 读之后可见——即"发布数据"：
生产者先填好 payload，再 release 写 flag；消费者 acquire 读到 flag 为真时，
保证看到的 payload 一定是填好的，两者之间不会有重排漏过来。
`relaxed` 只保证原子性不提供同步，适合纯计数（统计量，不参与逻辑判断）。
面试口径："默认 seq_cst 不出错；明确是'发布一个数据块给消费者'的场景，用 release/acquire 换性能；纯计数用 relaxed。"

## 高频追问

- **为什么需要内存序，CPU 不是保证缓存一致吗？** 一致性保证"最终看到同一个值"，不保证"按程序顺序看到"；编译器和 CPU 都会重排，同步对就是给重排画边界。
- **acquire 对应哪些操作？** load（读端）；release 对应 store（写端）；RMW 的 acq_rel 两边都算。
- **CUDA 有对应物吗？** 有——`__threadfence()`、`atomicAdd(..., memory_order)` 语义、`cuda::atomic`（libcu++），生产者-消费者 warp 间同步同样画 fence，思想同构。

## 记忆钩子

"release 是'货装好了再举旗'，acquire 是'看见旗才取货'；relaxed 只数数不传话。"

**人话版**：三个内存序各管一件事——
**release**（写在生产者侧）：保证"举旗之前做的所有事"（比如填好的数据）对对方可见——先装货再举旗；
**acquire**（读在消费者侧）：保证"看到旗之后读到的数据"是完整的——见旗才取货；
**relaxed**：只保证这个变量自己不出错（原子性），不提供任何"让别人看到我的其他修改"的保证——
只适合纯计数。
