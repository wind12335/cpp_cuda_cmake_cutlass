# 27 explicit 干嘛的：禁隐式转换

## 面试口述版

单参数构造函数（或可"单参调用"的多参构造）会自动成为**隐式转换通道**：
`void f(Widget w)` 遇到 `f(42)` 会拿 42 静默构造一个临时 Widget —— 有时方便，更多时候是事故：
类型本不该互通却被隐式转换打通、临时对象匿名生灭、重载决议变得不可预测。
`explicit` 把这条通道关掉：**只允许显式构造**（`Widget(42)` / `static_cast`），
隐式转换和拷贝初始化 `Widget w = 42;` 直接编译报错，把"类型混用"提前到编译期暴露。
准则：**单参构造默认写 explicit**，确认"该类型之间转换是自然语义"再放开
（`std::string` 从 `const char*` 隐式转是刻意设计的便利，属于少数派）。
C++11 起 explicit 也可修饰多参构造（禁 `= {a, b}` 列表初始化）和转换运算符（explicit operator bool）。

## 高频追问

- **explicit operator bool 解决什么？** 让 `if (stream)` 合法（显式语境转 bool）同时禁止 `int x = stream` 这种荒唐转换——"上下文转换"。
- **拷贝初始化和直接初始化区别？** `Widget w = 42;`（拷贝初始化，走隐式转换，explicit 拦截）；`Widget w(42);`（直接初始化，explicit 不拦）。
- **工程教训？** 我封装过"CUDA 设备 id"和"流 id"两个类型，不 explicit 的话函数参数传混了照样编译通过，运行期才炸——explicit 是零成本类型安全。

## 记忆钩子

"单参构造默认 explicit；隐式转换是给未来自己埋的雷。"

**人话版**：只有一个参数的构造函数（或能只传一个参数调用的）会被编译器当成"自动类型转换通道"——
`void f(DeviceId d)` 遇到 `f(42)` 会拿 42 **悄悄构造**一个临时 DeviceId。多数时候这不是你想要的：
类型混用编译不报错，运行期才炸。`explicit` 把这条自动通道关掉，必须显式写 `DeviceId(42)` 才行——
把错误提前到编译期暴露。经验：单参构造一律先写 explicit，确认转换语义自然再摘掉。
