# 19 Roofline：判断访存受限还是计算受限

## 面试口述版

Roofline 把任何 kernel 摆在一张图上：横轴**算术强度 I = FLOPs / Bytes（从显存搬运的字节数）**，
纵轴可达性能。形状像屋顶：左侧**斜坡是带宽屋顶**（性能 = I × 带宽，访存受限），
右侧**平顶是算力屋顶**（性能 = 峰值 FLOPS，计算受限），拐点 I* = 峰值算力 / 峰值带宽。
用法三步：① 数 FLOPs 和显存字节数（含读写双向）算出 I；② 对比 I*（4060 Laptop 量级：
~10 TFLOPS ÷ 272GB/s ≈ 37；H100 FP16 TC 约 990/3350 ≈ 0.3 → 用 TFLOPS/GBs 统一单位别搞混）；
③ I < I* 就是访存受限，往"减搬运/提复用"优化；I > I* 才轮到压榨计算单元（Tensor Core、流水线）。
经典定位：elementwise/reduce/softmax 的 I≈1-4（访存受限）；大 GEMM tile 后 I 能到几百（计算受限）；
attention 在大 N 前是访存受限（FA 就是在治这个）。
价值：**先定位再动手**——访存受限的 kernel 去手写 MMA 是白费劲，反之亦然。

## 高频追问

- **统计 Bytes 时漏了什么最常见？** 中间结果写回（softmax 的 N² 矩阵）、非合并访问放大的事务数、跨层（L2 命中与否）——精确版用 ncu 实测 DRAM 流量，别手数。
- **80% 峰值就到顶了吗？** 还要看指令效率：计算受限 kernel 也要查 warp state（stall 原因）、寄存器 spill、Tensor Core 利用率。
- **举例说出你课题里的 roofline 思维？** 通信受限 vs 计算受限的 overlap 判断：当通信带宽屋顶低于计算屋顶时才值得藏，且藏的上限 = min(两边)——cost model 就是集群版 roofline。

## 记忆钩子

"强度 = 计算量 ÷ 搬运量；斜坡看带宽，平顶看算力；先找自己在屋顶哪一段，再决定动哪刀。"

**人话版**：**roofline（屋顶模型）**给每个 kernel 定位：横轴是"算术强度"= 做了多少次计算 ÷ 搬了多少
字节；纵轴是实际性能。图形像屋顶：左边一段**斜坡**——性能被显存带宽封顶（搬运受限，优化方向是
少搬数据/多复用）；右边**平台**——性能被计算单元封顶（算力受限，优化方向是压榨 Tensor Core）。
先算出自己在斜坡还是平台，再决定动哪一刀——顺序反了全是白费劲。
