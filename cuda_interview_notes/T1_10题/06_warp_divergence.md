# 06 Warp Divergence

## 面试口述版

同一 warp 的 32 线程**锁步执行**，遇到 if/else 分支时硬件把"走 true 的线程"和"走 false 的线程"
**分成两条路径串行执行**，各走完再合流——两段加起来的时间 = 两段串行之和。
两个重要澄清（区分度高，答对加分）：
① **divergence 只在 warp 内有代价**：不同 warp 之间走不同分支无所谓——所以"按 threadIdx 低于 16 分支"很糟，"按 blockIdx 分支"没成本；
② 短分支 + 编译器能用**谓词（predication）**消除的场景（如 `x = c ? a : b` 简单赋值），两条路径其实都会算但只写一边，代价可忽略。
优化套路：让分支条件在 warp 内一致——数据重排（按条件排序/分桶）、把分支提为"整个 block/warp 级"决策、用算术技巧替代分支（如 `max/min` 替代 if）。

## 高频追问

- **if 里只放 1 个线程走的长循环，代价多大？** 其他 31 个线程陪着空转（掩码遮蔽），warp 时间全耗在这——最差情况吞吐掉 32 倍。
- **reduce 的树形归约为什么要"交错寻址"而不是"顺序相减"？** 顺序方案后半段活跃线程数 < 32，warp 内严重分歧 + idle lanes；交错方案每步活跃线程正好是前缀，无分歧（LeetCUDA reduce 系列的第一课）。
- **怎么定位？** ncu 源码级分析（Source Counters）看 branch efficiency；症状是"逻辑简单的 kernel 却有奇怪的指令数膨胀"。

## 记忆钩子

"warp 锁步，分叉变串行；分歧按 warp 算，别按 block 算；归约交错走，队形不散。"

**人话版**：warp 里 32 个线程执行指令是**步调一致**的，遇到 if/else 时只能先让走 if 的线程执行、
再让走 else 的执行——两段串行，时间相加。两个澄清：**分歧只在 warp 内有代价**（不同 warp 各走
各的分支无所谓，所以判断条件写在 block 级没事、写在 warp 内成员级别才危险）；规约这种场景要用
**交错寻址**（每步活跃线程排成连续一队），否则活跃线程越缩越散、warp 内分叉越来越重。
