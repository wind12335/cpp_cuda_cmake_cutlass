# NET-01 TCP 三次握手 / 四次挥手 / TIME_WAIT

## 面试口述版

**三次握手**：SYN → SYN+ACK → ACK。为什么三次？核心是**同步双方的初始序号**并确认"双方的收发能力都正常"——
两次不够：历史上的迟到旧 SYN 会让服务端建起幽灵连接空耗资源；四次多余。
**四次挥手**：FIN → ACK → FIN → ACK。为什么比握手多一次？因为**关闭是半双工的**：
被动方收到 FIN 后可能还有数据没发完，要先 ACK"知道你要关了"，发完自己的再发 FIN。
**TIME_WAIT**：只出现在**主动关闭方**，停留 2MSL（60s~2min；MSL = Maximum Segment Lifetime，
一个 TCP 报文在网络里被允许存活的最长时间，2MSL = 上行 + 下行各一趟，确保旧包彻底死绝）。
目的：①让网络里迷路的旧包自然消亡，
防止串进相同四元组的新连接；②保证对端能收到最后的 ACK（丢了还能重发）。
工程副作用：高频短连接把客户端端口耗尽/服务端积压——解法：长连接/连接池/`SO_REUSEADDR`（服务端重启不被卡）。

## 高频追问

- **大量 TIME_WAIT 出现在服务端怎么办？** 说明服务端在主动断连——设计上让客户端先关，或改长连接；`tcp_tw_reuse` 只对出站连接有效且要配时间戳。
- **SYN Flood 是打什么的？** 打半连接队列（收到 SYN 不回 ACK）——syncookie 用地址编码序号反制。
- **和分布式训练的关系？** 训练集群 rank 间长连接常驻，基本没有 TIME_WAIT 烦恼；但运维脚本频繁 ssh/拉起任务时会遇到——知道成因就能解释"为什么刚 kill 的任务端口重启报 Address already in use"。

## 动手绑定

`demos/net1_tcp_timewait.c`：进程内起服务端，客户端主动关闭 20 次，然后用 `ss` 数出 22 个 TIME_WAIT。

```bash
g++ -O2 -pthread demos/net1_tcp_timewait.c -o /tmp/net1 && /tmp/net1
# 实测: TIME_WAIT 数量 22 (20 个客户端 + 少量残留), 用 ss -tan state time-wait 可亲眼看到
```

## 记忆钩子

"握手三次同步序号，挥手四次因为半双工；谁先关谁 TIME_WAIT，等两轮报文寿命让旧包死透。"

**人话版**：**三次握手**（SYN → SYN+ACK → ACK）是为了让双方确认"我和你的收发能力都正常"、
并同步初始序号——两次不够（迟到的旧连接请求会建出幽灵连接）。**四次挥手**多一次，是因为关闭是
**半双工**的：收到对方 FIN 后我可能还有数据没发完，要先确认"知道你要关了"，发完自己的再发 FIN。
**TIME_WAIT** 只出现在**主动关闭的一方**：原地等 2×MSL（报文最大存活时间，来回两趟），
让网络里迷路的旧包自然过期，防止串进相同端口的下一代连接。
