# NET-03 epoll 为什么快（LT / ET）

## 面试口述版

**select/poll 的问题**：每次调用把**全部** fd 集合从用户态拷进内核，内核**线性扫描**所有 fd 查就绪——
连接一多（万级），拷贝和扫描都是 O(n)，绝大部分 fd 根本没事件。
**epoll 三件套**：`epoll_create`（内核建实例）、`epoll_ctl`（fd 注册进红黑树，只注册一次）、
`epoll_wait`（只返回就绪列表）。就绪怎么来？驱动/协议栈回调把事件 fd 挂进**就绪链表**——
epoll_wait 只看链表，复杂度 O(活跃连接数) 而非 O(总连接数)，百万连接也不慌。这就是"快"的全部来源。
**LT vs ET**（demo 一演就懂）：
**LT 水平触发**（默认）：只要还有数据没读完，每次 epoll_wait 都会报——好写，忘了读也丢不了；
**ET 边缘触发**：只在状态"从无到有"变化时报**一次**——少唤醒、高效，但必须**非阻塞 fd + 循环读到 EAGAIN**，
否则剩下的数据永远没人管（连接饿死）。

## 高频追问

- **demo 亲手踩的坑（真事）**：在阻塞 pipe 上做"读到 EAGAIN"——阻塞 fd 读空会**永久挂起**而不是返回 EAGAIN，程序直接卡死。这正是"ET 必须配非阻塞"的原因，比背十遍都深刻。
- **epoll 就一定比 select 快吗？** 活跃连接占比高（几乎全活跃）时优势缩小（都得起回调处理）；它的赢面在"海量连接、少数活跃"的 C10K 场景。
- **和 GPU 的关系？** 思想同构：epoll 用"就绪链表"替代"轮询全部"，正如 CUDA 用"事件驱动回调"替代"CPU 忙等 GPU"——stream callback / cudaEventSync 都是把同步成本摊到事件粒度。

## 动手绑定

`demos/net3_epoll_lt_et.c`：pipe 上演示 LT 连报 3 次 vs ET 只报 1 次 + EAGAIN 抽干姿势。

```bash
g++ -O2 -pthread demos/net3_epoll_lt_et.c -o /tmp/net3 && /tmp/net3
# LT: 返回 1,1,1   ET: 返回 1,0,0 —— 一目了然
```

## 记忆钩子

"select 全民普查，epoll 只看活跃名单；LT 唠叨，ET 高冷——高冷就必须非阻塞 + 抽到 EAGAIN。"

**人话版**：**select/poll** 每次调用都要把**所有**监听的连接挨个查一遍（全民普查），连接一多就慢；
**epoll** 只返回**有事件**的连接名单（活跃名单），百万连接也只看活跃的那几十个——这就是快的来源。
两种通知模式：**LT（水平触发）**是唠叨型——数据没读完每次都提醒你；**ET（边缘触发）**是高冷型——
只在"从无到有"时提醒一次，所以必须一次把数据**抽干**（循环读到 EAGAIN，即"读无可读"的错误信号），
而且必须配非阻塞 fd，否则抽干时读空会永久卡住（我们的 demo 就真卡过）。
