# OS-04 死锁：四条件与预防

## 面试口述版

死锁四条件（缺一不可，破任一即解）：①**互斥**——资源同一时刻一人；②**占有且等待**——拿着 A 等 B；
③**不可抢占**——不能硬抢别人的；④**循环等待**——形成"你等我、我等你"的环。
工程上最常用的是**破第 4 条**：全局固定加锁顺序（比如按地址/编号排序），所有线程按同一顺序拿锁，环就成不了；
C++17 的 `std::scoped_lock lk(a, b)` 一次申请多把、内部用免死锁算法，等于自动帮你破。
其他手段：`try_lock` 失败就释放重来（破"占有且等待"）；`std::timed_mutex` 超时兜底（检测+放弃）；
锁粒度合并（一次拿全所有需要的）。
**检测诊断**：`gdb -p <pid>` 后 `thread apply all bt`——两个以上线程栈顶都停在 `__lll_lock_wait` 基本确诊；
或 `cat /proc/<pid>/task/*/stat` 看线程都卡在 futex wait。
重要事实（demo 第一幕演的）：**死锁进程无法自救，只能杀**——所以预防 > 事后检测。

## 高频追问

- **现场怎么快速定位训练/服务 hang 是不是死锁？** 先看 CPU：死锁线程是 0% CPU 的 futex 睡眠（和死循环 100% 区分）；再 gdb 看两个以上线程卡在同一对锁。
- **分布式版本？** 各 rank 上锁顺序不一致 = NCCL collective 调用顺序不一致 → 集合通信 hang——这就是"所有 rank 必须以相同顺序调用 collective"的原因，你在多机微调里遇到过（和 NCCL 排查口诀能接上）。
- **GPU 联动**：CUDA 多流 + event 的 `cudaStreamWaitEvent` 依赖成环 = 死锁等价物，graph capture 会直接报错禁止。

## 记忆钩子

"互斥、占有等、不抢占、循环等——环是核心，全员同序环不成；死锁只能杀，预防是正道。"

**人话版**：死锁四条件——①**互斥**（资源一次一人用）②**占有且等待**（攥着 A 等 B）③**不可抢占**
（不能硬抢别人的）④**循环等待**（你等我、我等你，绕成圈）。四个**同时成立**才死锁，所以破掉任意
一个就能预防——最常用的是破第 ④条：所有线程按固定顺序加锁（比如都先 A 后 B），圈就绕不起来。
死锁进程无法自救只能 kill，所以功夫全在预防。
