# OS-03 互斥锁 vs 自旋锁：选用场景

## 面试口述版

分叉点就一个：**拿不到锁时怎么办**。
**互斥锁（mutex）**：睡进内核等待队列，让出 CPU——"抢不到就睡"，醒来有唤醒开销
（底层是 **futex** 机制：fast userspace mutex，内核里一个"能睡眠的原子计数器"；无竞争时加锁解锁
纯用户态原子操作就完成，只有真抢不上才陷入内核睡眠——所以"无竞争时其实只是用户态原子 CAS，很快"）；
**自旋锁（spinlock）**：原地忙等烧 CPU——"抢不到就转圈"，拿到锁的反应是纳秒级，但等久了纯属浪费核。
选用标准：**临界区极短（几十 ns~百 ns）且多核可烧 → 自旋**（内核中断路径、无锁化尝试）；
**临界区长或有 IO、用户态服务 → mutex**（让出 CPU 给别人干活）；
**就是保护一个计数器 → 别上锁，atomic**。
本机实测：无竞争 mutex 加锁解锁 ~20ns 量级（一次原子操作级）；高竞争下 mutex 吞吐反而好于"天真的自旋"（烧核浪费）——别背"自旋一定快"。

## 高频追问

- **mutex 无竞争时也要系统调用吗？** 不用——futex 机制：无竞争路径纯用户态原子 CAS，只有真冲突才陷入内核睡眠；这就是"快路径/慢路径"设计。
- **自旋锁在单核机器上有意义吗？** 几乎没有——自旋的每一拍都在浪费唯一核的时间片（内核抢占式自旋锁有特殊处理，用户态没有）。
- **混合方案？** 先自旋几拍再睡眠（adaptive mutex / 短自旋），兼顾两者——能说出这个词就是加分。
- **GPU 联动**：CUDA `atomicAdd` 高竞争同样"排队烧带宽"，解法同源：分桶/树形归约，把"多线程抢一个"变成"各自记小账再合并"。

## 记忆钩子

"睡是 mutex，转是自旋；短平快转一圈，长活计睡大觉；一个计数器用 atomic，什么都别锁。"

**人话版**：抢不到锁时两种反应——**mutex 选择睡**（让出 CPU 给别人干活，醒来有唤醒开销，
适合临界区长、或有 IO 的场景）；**自旋锁选择原地转圈干等**（反应是纳秒级，但等久了纯烧 CPU，
适合临界区极短且核多的场景）。如果只是保护一个计数器，两种都别用，直接 **atomic**。
