# OS-06 用户态 / 内核态与系统调用

## 面试口述版

CPU 分**特权级**（x86 是 ring0/ring3）：用户态不能碰硬件/页表/中断——防应用搞坏系统和彼此。
用户态要内核做事就走**系统调用**：一条 `syscall` 指令陷入内核 → 保存现场 → 按调用号查系统调用表 →
内核执行 → 恢复现场返回。代价 ~100-300ns，是普通函数调用的**百倍**——所以"系统调用次数"本身是性能指标。
内核的应对三板斧：**vDSO**——把时钟这类只读数据直接映射进用户空间，`clock_gettime` 根本不陷入
（实测 15ns vs 真 syscall 167ns，差 11 倍）；**批处理**——一次 syscall 干一批活（read 1MB 而非 1KB）；
**减少调用**——零拷贝（sendfile 少两次拷贝两次调用）、epoll 一次等一批 fd（联动 NET-03/04）。
中断/异常是另外两个进内核的入口：中断是异步的（网卡来包）、异常是同步的（缺页、除零）。

## 高频追问

- **上下文切换和模式切换的区别？** 模式切换（syscall）同一进程内换特权级，便宜；上下文切换换进程/线程（换寄存器组+地址空间），贵一个量级——一次 syscall 不一定切换上下文。
- **为什么 getpid 被缓存了？** glibc 老版本把结果缓存在用户态避免陷入；新内核（4.9+）因容器 PID namespace 问题又走真调用——demo 里直接用 `syscall(SYS_getpid)` 强制真陷入，测出来的才是切换成本。
- **和 GPU 的关系？** 每次 cudaLaunchKernel/memcpy 都要经过驱动（ioctl 陷入内核）——推理引擎用 CUDA Graph 把上百次 launch 合成一次，本质就是"摊薄陷入次数"，与 vDSO/epoll 同一思想。

## 动手绑定

`demos/os6_syscall_vdso.c`：vDSO vs 真 syscall vs glibc 封装，三档成本实测。

```bash
g++ -O2 -pthread demos/os6_syscall_vdso.c -o /tmp/os6 && /tmp/os6
# 实测: vDSO ~15ns / syscall ~167ns
```

## 记忆钩子

"陷入一次三百纳秒；省调用就是省命：vDSO 搬进来、批处理并起来、epoll 攒一波。"

**人话版**：系统调用（"陷入"内核）一次要保存现场、切特权级、查表、恢复现场，约 100-300ns——
是普通函数调用的百倍。所以高手的优化方向全是**少陷入**：**vDSO** 把时钟这类只读数据直接映射进
用户空间（读时间根本不用进内核）；**批处理**一次干一批活（一次 read 1MB 而不是读一千次 1KB）；
**epoll** 一次等一万个网络连接、只返回有事的那些。
