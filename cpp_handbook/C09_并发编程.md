## §C09.0 怎么"看见"多线程？（新手第一问）

三个层次，从土到洋：

**① 最土最有效：打印 + 线程编号**（每个实验都这么干）：

```cpp
#include <thread>
#include <functional>   // ← std::hash 的家(不在 <thread> 里!)
printf("[线程%zu] 干到第 %d 步\n",
       std::hash<std::thread::id>{}(std::this_thread::get_id()), i);
```
（std::hash 是什么、为什么能这样用 → **C04 §C04.3.3 讲透了**：unordered_map 的"分桶器"。）

多个 `[线程xxx]` 的输出**交错出现**，就是并行的直接证据（本章 lab 全程这样观察）。

> **这行 `std::hash<std::thread::id>{}(...)` 是什么写法？**——三步叠一行，全是学过的：
> - `std::hash<std::thread::id>` 是个**类**（functor，C08.6）——`std::hash<T>` 按 T **特化**（C08.4），给 thread::id 算哈希数的版本；
> - `{}` 建一个**匿名临时对象**；
> - `(...)` 调它的 `operator()`——对象像函数一样被调用。
> 等价于 `auto h = std::hash<std::thread::id>{}; h(id);`（实测两版结果相同）。
> 你在 C04 见过同款：`std::sort(..., std::greater<int>{})`——那个 `{}` 建的也是 functor 对象。
> **为什么绕这一遭**：`thread::id` 没法直接 printf（它不是整数），hash 成数字才能打印；
> 用 `std::cout << std::this_thread::get_id()` 可以直接打印（它支持 <<，但不支持 %zu）。
> **记法**：`类{}(参数)` = "临时 functor 对象当场调用"，现代 C++ 遍地都是。

**② 打断点看：gdb 的线程视角**。

**gdb 是什么**：GNU Debugger，Linux 下 C/C++ 的**调试器**——不加 printf、不重编译，
让程序**停在指定行**，停住时可以看变量、看调用栈、逐行执行。你之前一直用 printf 调试
（重编译跑一遍看输出），gdb 是"现场暂停检查"。VSCode 里按 F5 的可视化调试，Linux 上
**底层就是 gdb**——按钮都一样，只是穿了马甲。

**生存五命令**（够用一辈子）：

| 命令 | 干什么 | 人话 |
|---|---|---|
| `break 文件:行号` 或 `break 函数名` | 设断点 | 跑到这就停 |
| `run` | 开跑 | 停在断点 |
| `print 变量` | 看变量值 | 停住时随便看 |
| `next` / `step` | 下一行 / 进函数 | 逐行走 |
| `continue` | 放行到下个断点 | 跑 |

**多线程专属**（程序停在断点时，**所有线程一起冻结**）：`info threads` 列出所有线程
（`*` 标当前所在的），`thread 2` 切到 2 号线程看它的栈（`bt`）。实测输出长这样：

```
(gdb) break worker
(gdb) run
Thread 2 hit Breakpoint 1, worker (id=7) at gdb_demo.cpp:4
(gdb) info threads
  Id   Target Id                                Frame
  1    Thread 0x7ffff7ea83c0 "gdb_demo"   worker (id=0) at gdb_demo.cpp:4
* 2    Thread 0x7ffff77ff640 "gdb_demo"   worker (id=7) at gdb_demo.cpp:4
(gdb) print id
$1 = 7
```

（`bt` 还能看到 `std::thread → pthread → clone` 的完整调用链——线程是怎么被造出来的，一眼见底。）
（F5 窗口里 Register 面板的 CPU/Segs/FPU/SSE/AVX/MMX 分组和 r/e 开头寄存器全家 → **C09b 专篇详解**。）

> **顺带拆透那行 printf（参数结构没讲清是我的锅）**：
> ```cpp
> printf("[线程%zu] 干到第 %d 步\n",
>        std::hash<std::thread::id>{}(std::this_thread::get_id()), i);
> ```
> printf 收**三个**参数：格式串 + 两个值（`%zu` 和 `%d` 两个占位符各对一个）。第二个参数
> 本身是**两层调用的嵌套**，拆开等价于：
> ```cpp
> auto id  = std::this_thread::get_id();        // ① 内层: 调【函数】get_id() → 返回 thread::id
> size_t n = std::hash<std::thread::id>{}(id);  // ② 外层: 调【functor对象】→ 哈希成数字
> printf("[线程%zu] 干到第 %d 步\n", n, i);      // ③ n 填 %zu, i 填 %d
> ```
> ——内层 `get_id()` 是**真函数**（住在 `std::this_thread` 命名空间里，问"我是谁"）；
> 外层是**functor 对象调用**（上一节的 `类{}(参数)`）。函数和 functor 在语法上都是
> `名字(参数)`，分不清时看名字是函数还是对象。

**③ 现象观察**：数据竞争实验里"同一段代码加不加锁结果差几千"——不看线程本身，看**共享数据的伤情**。

**人话版**：调试器是"冷冻切片"（全停，逐个看）；打印是"行车记录仪"（跑完回放）。并发 bug 一般靠②③组合拳。

## §C09.1 创建线程 std::thread

**作用**：启动一个并行执行流。

```cpp
#include <thread>
void work(int id) { /* ... */ }
std::thread t1(work, 1);        // 启动线程执行 work(1)
std::thread t2([]{              // lambda 版: []捕获列表(空=不带外面的变量)
    printf("我是lambda线程\n"); //   {}里就是普通函数体 —— C02 §C02.7 的知识
});                             //   好处: 任务代码写在启动处, 一眼看完
t1.join();
t2.join();
```

### §C09.1.1 join 不是"加入队列"，是"等它干完并回收尸体"

线程生命周期：**创建 → 运行 → 函数跑完（僵尸态，占着资源）→ 被 join/detach 回收**。

- `t.join()` = 主线程**站在原地等**它跑完，然后回收它的资源。join 之后 t 就是个空壳（不可再 join）。
- `t.detach()` = 放养：从此不管它死活（进程退出时一并结束）——危险，主线程退出后它访问的任何东西都可能没了，初学别用。
- **既不 join 也不 detach 就让 t 析构 → `std::terminate` 当场崩**（实测退出码 134，
  报 `terminate called without an active exception`）——C++ 用硬崩逼你表态。

**人话版**：thread 对象像"工牌"。join = 站门口等工人下班、收回工牌；detach = 工牌扔了随他去；
拿着还在职的工牌直接走人（析构）= 保安直接拉闸（terminate）。

### §C09.1.2 线程的栈：`int x` 到底住哪（实测）

`test_thread()` 里的 `int x = 0; int y = 100;`——**家在栈区**（C03 §C03.9），精确说是
**main 线程栈上 test_thread 的栈帧里**（rbp~rsp 框定的格子，gdb 实测 &x 就落在其中；
x 和 y 是**紧挨着的两格**，实测地址差 4 字节）。但三条延伸认知更重要：

1. **家在栈，干活进寄存器**：`x++` 的机器码是"从栈把 x 装进 eax → eax 加一 → 写回栈"
   （C09b：寄存器是工位，栈是宿舍）；
2. **每个线程有自己的栈**（实测：t1 里局部变量 `inner` 的地址 0x75af… 和 main 栈的
   0x7ffe… 差十万八千里——两块独立内存）；
3. **`[&]` 捕获 = 把 x 的地址塞给线程**：t1 通过地址**跨栈访问** main 栈上的格子
   （实测：线程里打印 `&x` 和 main 里的完全相同）。这就是数据竞争的物理图景——
   两个执行流拿着同一把门钥匙（地址）挤进同一个格子。

（对照：`thread_local int x` 则是每线程一份，靠 fs/gs 寻址各自的家——C09b Segs 组。）

## §C09.2 数据竞争与 std::mutex

**作用**：两个线程同时写一个变量 = 未定义行为。mutex 保护"同一时刻只有一个线程进临界区"。

```cpp
#include <mutex>
std::mutex m;
long counter = 0;

void worker() {
    for (int i = 0; i < 100000; ++i) {
        m.lock();               // 上锁: 我进屋锁门, 别人调 lock 只能在门口等
        ++counter;              // 临界区(屋里同时只有一个人)
        m.unlock();             // 解锁: 出门放行下一位
    }
}
```

### §C09.2.1 概念澄清（两个高频混淆）

**① mutex（互斥锁）≠ 信号量（semaphore）**。你理解的"给操作上锁、多个线程不能同时
++counter"——**效果说对了**，但机制名是 mutex：**同一时刻恰好 1 个**线程进临界区
（互斥）。信号量（semaphore）是"同时最多 N 个"（计数闸门），C++20 才有
`std::counting_semaphore`，本手册用不到。**日常说"上锁"= mutex**。

**② `m.lock()` 和 `weak_ptr.lock()` 不是一回事！** 纯属撞名（你猜对了）：

| | mutex 的 lock() | weak_ptr 的 lock() |
|---|---|---|
| 干什么 | 我进屋锁门，别人等着 | "查活+借卡"：借一个 shared_ptr |
| 所属机制 | 互斥/并发 | 引用计数/智能指针 |
| 记法 | **锁门** | **借卡** |

【前置：C06 RAII】手写 lock/unlock 在异常路径会漏 unlock——用 `std::lock_guard<std::mutex> lk(m);`
（构造加锁、析构解锁，第 16 题的经典应用）。

### §C09.2.2 mutex 不是模板：锁的是"一段代码"，不是"一个数据"（新手高频误解）

`std::mutex<std::thread>` 这种写法不存在——**mutex 没有模板参数**，写 `std::mutex m;` 即可。
误解根源：以为锁要"指定锁谁"。真实设计是**两种保护哲学**（对照实测）：

| | `std::atomic<long>` | `std::mutex` |
|---|---|---|
| 哲学 | **给数据穿防弹衣** → 所以必须填数据类型 | **给房间装门锁** → 不认识房里的东西 |
| 模板参数 | 被保护**数据**的类型 | 无 |
| 守几个数据 | 1 个（就包着的那个） | **任意个**（锁的是 lock~unlock 之间的**代码路径**）|

```cpp
std::mutex m;             // ✓ 就是个锁, 不记录"锁谁"
long balance = 1000, ledger = 0;   // 约定: m 守这对变量的【一致性】
void transfer(long amt) {
    m.lock();             // 锁的是: 从这行到 unlock 的整段代码
    balance -= amt;       // ┐ 两步是个整体(不变量), 中途插队会看到
    ledger  += amt;       // ┘ "钱扣了账没记" —— 一个 mutex 守两个变量
    m.unlock();
}
// 实测: 两次并发转账后 balance=700, ledger=300, 恒等式 balance+ledger=1000 成立
```

**锁和数据的关联只存在于命名/纪律里**（所以惯用 `std::mutex m_counter;` 配 `counter`），
编译器**不检查**谁配谁——用错锁保护数据是并发 bug 的经典来源（代码审查主题）。
而 `std::lock_guard<std::mutex>` 的模板参数填的是**锁的类型**（门童认锁的型号），
更不是数据的类型。

**人话版**：atomic 是"给变量穿防弹衣"（所以报尺码=数据类型）；mutex 是"给房间装门"
（门不认识房里的家具，只管一次进一个人）；lock_guard 是"自动门童"（模板参数填门锁型号）。

**记忆钩子**："**atomic 穿衣服（要尺码），mutex 装门（认路不认货）**。"

### §C09.2.3 为什么输出"一会x一会y"？（stdout 也是共享资源，实测）

两个线程的输出交错，"抢"的其实是**两样东西**，性质完全不同：

1. **CPU 核——大概率根本不用抢**：你的机器 32 核，两个线程很可能各占一个核
   **同时跑（真并行）**，不是轮流用一个核。交错的不是"计算"，是下面这位。
2. **stdout 终端——全世界只有一支笔**：`std::cout` 是共享资源，谁抢到笔谁写一个字。
   而且一条 `cout << "[" << tag << i << "]"` 是 **4 次独立写入**——另一线程可以插在
   中间，产生**半行插半行的串行**（实测 3000 行里 74 行被插）：

```
[AB1764]        ← A 写了"["和"B"字…不对, 是 A 写 [ 后 B 插进来写了 B…
[[BA6177]       ← 双方各写了一半
```

**解法**（生产代码日志的标准姿势）：把整条输出包进锁里——实测加锁后 3000 行**零串行**，
每行完整；但 A/B 的**先后顺序依然交错**——因为**调度顺序天生不确定**，锁只保证"每行
不被插"，不保证"谁先谁后"。这也是并发 bug 难查的根源（§C09.0 ③）：每次运行交错都不同。

```cpp
std::mutex io_m;
{   std::lock_guard<std::mutex> lk(io_m);   // 整条 cout 一口气写完
    std::cout << "x:" << x << std::endl; }
```

**记忆钩子**："核可能不抢，笔只有一支；锁保行完整，不保先来后到。"

### §C09.2.4 锁不保证先后：`mt.lock(); t1.join();` 为什么排不出"先x后y"（实测）

新手常见尝试：想"先输出完 x 再输出 y"，于是把 `t1.join()` 包进锁里——**无效**，三个原因：

1. **锁要"共用"才有意义**：你的 mt 只有 main 碰过，t1/t2 从没用它——没有竞争对手，
   锁等于没锁（你在家装门锁，别人根本不走你家门）。
2. **线程在构造那一刻就开跑了**（不是 join 才跑）：main 走到 `mt.lock()` 时，
   t1/t2 早就在并发打印了；join 只是"等它跑完"，不是"现在让它跑"。
3. **锁的语义只有"不同时"，没有"谁先谁后"**（§C09.2.2 末尾同一句话）。

实测 10 次：你的写法**有时碰巧**先x后y（t1 恰好在 main 唤醒 t2 前跑完）、有时 y 插进
x 队伍（`x5 y15 y14… x6`）——**碰巧有序 ≠ 保证有序**。

**想要"先x后y"的三种正确姿势**：

```cpp
// ① join 完 t1 再【启动】t2 —— 最简单, 实测严格有序; 代价: 变串行(y 干等 x)
std::thread t1(...); t1.join();
std::thread t2(...); t2.join();

// ② 两线程共用同一把锁包住整条 cout —— 只保证"行完整", 顺序依然交错(§C09.2.2 已测)

// ③ cv/future 让 t2 等 t1 的"完工信号" —— 既保持并发结构又有先后(C09.4/C09.5 的主场)
```

⚠️ **附带一个经典死锁警告**：如果 t1 内部**也用 mt** 锁输出，而 main **拿着 mt 等
`t1.join()`——t1 等 mt 解锁才能打印，main 等 t1 结束才能解锁 → **互相等死**。
规矩：**不要拿着锁去等别人**（锁内不做阻塞等待：不 join、不 sleep、不等 cv）。

**记忆钩子**："线程生来就跑，join 只是收尸；锁管同时不管先后，先后要靠信号。"

## §C09.3 std::atomic：无锁的原子变量

**作用**：单个变量的加减/读写不需要锁——更轻。

### §C09.3.1 atomic 到底把 long 包在了什么里

不是包在"盒子"里，是**把"读-改-写"焊成不可分割的一步**——直接落到**硬件原子指令**
（x86 的 `lock xadd`/`cmpxchg`）上。两个线程同时 fetch_add，硬件保证一次只赢一个，
另一个重试，**结果一个不丢**（裸 `++counter` 是三步：读、加、写，两线程交错就互相覆盖——
丢更新，T2-22 有实测）。

### §C09.3.2 你的四个具体问题（全部实测）

**① 尖括号里能放自创类/结构体吗？**——能，但有条件：**平凡可拷贝**（POD，无自定义
构造/析构/虚函数）才编得过（实测 `atomic<Pod>` ✓，Pod={int,float}）。但注意：结构体只能
load/store 整体换（内部可能退化为带锁实现），**fetch_add 这类算术原子只对整数/浮点标量有**。

**② fetch_add 只能自增？**——不止！整个家族：
`fetch_sub`（减）、`fetch_and/or/xor`（位运算）、`exchange`（无条件换成新值）、
`++/--`，以及无锁编程的基石 **`compare_exchange_strong`（CAS："如果还是旧值就换成新值"**，
实测见 lab）。CAS 是所有无锁数据结构的发动机（面试高级话题的门票）。

**③ `count.load()` 是唯一读法？**——不是！**`long v = count;` 也能编**（atomic 提供了
隐式类型转换，内部就是调 load()）。两种等价（实测都是 42），`load()` 只是**更显眼地
告诉你"这是原子读"**——风格上推荐，语法上不强制。写 `count.store(5)` 和 `count = 5`
同理。

```cpp
std::atomic<long> count{0};
count.fetch_add(41); count.fetch_add(1);
long a = count.load();   // 写法① 显式(推荐)
long b = count;          // 写法② 隐式转换(也合法, 等价①)
```

**选择标准**：保护单个变量 → atomic；保护"一段逻辑/多个变量" → mutex。
（前置：T2-22 有丢更新实测、T2-23 内存序。）

## §C09.4 条件变量：线程间的"叫醒服务"

**作用**：让线程"没活就睡，有活被叫醒"——生产者消费者模型的核心。

### §C09.4.1 unique_lock 是什么？和 unique_ptr 有关系吗？

**没有亲戚关系，只是同一个 RAII 哲学的两次应用**（起名撞了风格）：

- `unique_ptr<T>`：RAII 管**内存**——构造时拿到指针，析构时 delete
- `unique_lock<mutex>`：RAII 管**锁的状态**——构造时 lock（`lk(m)` 即锁门），析构时 unlock

都叫 unique 因为都是"**独占管理权、离开作用域自动收尾**"（C06 RAII 的并发版）。
`std::lock_guard` 是它的简化版（更轻但不能中途解锁）；条件变量的 wait 需要"能解锁再
重新锁"，所以**必须配 unique_lock**（lock_guard 做不到）。

### §C09.4.2 wait 那一行逐帧拆解（最容易懂反的地方）

```cpp
std::unique_lock<std::mutex> lk(m);   // ① 锁门(和别的线程互斥)
cv.wait(lk, []{ return ready; });     // ② 见下三步
```

`wait(lk, 谓词)` 的真实动作（**注意顺序，和你猜的相反**）：

```
1. 检查谓词 []{ return ready; } —— 就是个无参、返回 bool 的小函数:
   "该我干活的条件(ready)成立吗?"
2. 成立 → 直接往下走(压根不睡)
3. 不成立 → 【解锁 lk, 睡觉】 ← 关键! 睡觉时是【放锁】的, 不然生产者怎么进来改 ready?
4. 被 notify 叫醒 → 【重新抢锁】 → 抢到后再查谓词 → 不成立继续睡, 成立才往下走
   (这就是"wait 内置循环"——防"叫醒了但条件又不满足"的假唤醒)
```

**实测铁证**（lab 里有完整版）：消费者睡在 wait 里时，生产者**能锁上同一把锁**改
ready——证明 wait 睡觉期间锁是放开的。

**而 `cv.notify_one()` 不碰锁！** 它只干一件事：**叫醒一个**睡着的线程（把它扔进
"抢锁排队"的队伍）。锁的释放发生在**通知方自己的 unique_lock/lock_guard 离开作用域**
的那一行（RAII）——和 notify 无关。`notify_all` = 叫醒全部。

**完整握手时序**（背下来）：

```
消费者: 锁门 → wait(谓词不满足: 放锁睡觉 zzz)
生产者: 锁门 → 改 ready=true → 出作用域[自动解锁] → notify_one()
消费者: 被叫醒 → 重新抢锁 → 查谓词✓ → 拿着锁干活 → 出作用域[自动解锁]
```

## §C09.5 future/async：拿"将来才有"的结果（完整版）

**解决什么问题**：`std::thread` 有个致命缺陷——**线程函数不能有返回值**！
你想"让别的线程帮我算个数，稍后取结果"，用 thread 就得：定义共享变量 + mutex +
cv 通知 + 手写等待——一套仪式。`async/future` 把这一套打包了：

```cpp
#include <future>
// async: 把任务丢出去(默认可能新线程) → 返回 future(期货凭证)
auto fut = std::async(std::launch::async, []{ return 6 * 7; });
// ... 主线程干别的 ...
int answer = fut.get();      // get(): 拿着凭证去取货, 没到货就等着 → 42
```

| 名字 | 角色 | 人话 |
|---|---|---|
| `std::async` | 启动器 | 把任务丢给别的线程，立刻给你一张凭证 |
| `std::future<T>` | 凭证 | T 是"将来能取到的货的类型"；get() = 取货（阻塞） |
| `fut.get()` | 取货 | 只能取**一次**（取完凭证作废）；没算完就等 |
| `std::launch::async` | 策略 | 强制新线程立刻跑（不写的话编译器可能"拖延到 get 才跑"= deferred，坑） |

**真实例子（lab 实测）：两个线程各算一半求和，汇总零 mutex**：

```cpp
long partial_sum(const std::vector<int>& v, size_t lo, size_t hi) {
    long s = 0;
    for (size_t i = lo; i < hi; ++i) s += v[i];
    return s;                                  // ← thread 做不到: 线程函数能返回值!
}
auto futA = std::async(std::launch::async, partial_sum, std::cref(big), 0, big.size()/2);
auto futB = std::async(std::launch::async, partial_sum, std::cref(big), big.size()/2, big.size());
long total = futA.get() + futB.get();          // 两个凭证取货相加, 无任何共享变量/锁
// 实测(4000万元素): 串行 8.6ms → 并行 5.4ms
```

**为什么它比"thread + 共享变量 + mutex + cv"好**：返回值通道、等待、异常（线程里抛的
异常能穿过 future 到达 get()）全部内建——**并发记账全免了**。

【延伸，用到再看】`std::packaged_task`（把函数打包成可取货的任务对象）、
`std::promise`（手动往 future 里塞值）——是 async 的底层积木。
【CUDA 相关】X04 的 host 双线程流水线就是 `async`/`thread` + stream 的组合。

## §C09.6 与 CUDA 的结合【CUDA 相关】

- 每个 host 线程可以有自己的 **CUDA stream**（G06），实现"线程 A 预取数据、线程 B 监控进度"；
- CUDA context 与线程的关系：多线程共用一个 context 时要注意同步（X04 手把手）；
- `std::thread` 里调 `cudaMemcpy` 完全合法——CUDA runtime 是线程安全的（同一 context 内串行化）。
