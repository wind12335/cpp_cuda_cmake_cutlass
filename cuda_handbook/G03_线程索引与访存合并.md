# G03 线程索引与访存合并 【核心】

## §G03.1 一维/二维/三维索引公式

**作用**：kernel 里第一件事永远是算"我负责哪个数据"。

```cpp
// 一维 (elementwise/reduce 最常用)
int i = blockIdx.x * blockDim.x + threadIdx.x;

// 二维 (矩阵/图像): 行列分开算
int row = blockIdx.y * blockDim.y + threadIdx.y;
int col = blockIdx.x * blockDim.x + threadIdx.x;
int idx = row * width + col;         // row-major: 行优先展开成一维

// 三维 (体数据): 再加 z
```

**启动端配套**：`dim3 block(16, 16); dim3 grid((w+15)/16, (h+15)/16); kernel<<<grid, block>>>(...)`

【前置：C01 §1.5 位运算】`blockIdx.x * blockDim.x` 这类乘法在 GPU 上极便宜，放心用。

## §G03.2 grid-stride 循环：一个线程干多个活

**作用**：数据量与线程数解耦——同一个 kernel 处理任意大小。

```cpp
__global__ void vecAdd(const float* a, const float* b, float* c, int n) {
    int stride = gridDim.x * blockDim.x;               // 全部线程的总数
    for (int i = blockIdx.x * blockDim.x + threadIdx.x;
         i < n; i += stride) {                          // 跳过全体人数继续干
        c[i] = a[i] + b[i];
    }
}
// 启动时甚至可以固定 grid = SM 数的倍数, 与 n 无关
```

好处：①不需要为每个 n 算 grid；②每线程多干活，摊薄启动/索引开销；③保持合并访存（相邻线程
仍处理相邻地址）。

## §G03.3 合并访存（Coalescing）【性能第一课】

**作用**：显存按"事务"搬运（一次 32/128B）。warp 内 32 个线程访问**连续地址** → 硬件合并成
少量事务；访问分散 → 最多 32 个事务，带宽利用率暴跌 32 倍。

```cuda
// ✓ 合并: 相邻 threadIdx 访问相邻元素
c[i] = a[i] + b[i];              // i = blockIdx*blockDim + threadIdx

// ✗ 不合并: 跨步访问 (stride=2 → 只用一半带宽)
int i = (blockIdx.x * blockDim.x + threadIdx.x) * 2;

// ✗ 不合并经典案例: row-major 矩阵按"列"读 (相邻线程的地址差一整个 width)
float v = A[col * width + row];
```

**修复模式（转置场景）**：用 shared memory 当中转——读入时合并、写 shared 时转置、写回时再合并
（第 05 章 + T1-05 实验验证）。

## §G03.4 SoA vs AoS：布局决定合并

```cpp
struct AoS { float x, y, z; };      // 交错存放: warp 读所有 x 时地址跨步 12B → 不合并
struct SoA { float x[N], y[N], z[N]; };   // 分列存放: 每个字段内部连续 → 合并 ✓
```

【CUDA 相关】粒子/顶点数据、权重布局都按 SoA 组织；你做通信 benchmark 时 buffer 布局同理。

## §G03.5 越界与保护

```cpp
int i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < n) { ... }          // 标准写法: grid 向上取整多出的线程在这里被拦住
```

【坑】不写保护 + grid 向上取整 = 越界写 = 显存被踩（可能表现为"后面某个 API 莫名报错"，
前置：面试 G10 排查三板斧）。
